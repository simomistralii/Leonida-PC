# What the related ports do that this runtime does not yet

**Status: a reading of other projects' source, 2026-11-24. Nothing here is measured in this repository yet.** Each
row is a fact another project records about what the title asks of a console API, the file it is recorded in, and
the place in this runtime that does something else. A row is a lead: check it with a test of your own, a measured
trace or a public specification before relying on it. The licence boundary for each project is in
[related_projects.md](related_projects.md); in short, facts only, never code.

Read at VIctory `97c78d1` (GPL-3.0-or-later). In VIctory's column, a path is under
`crates/victory-hle/src/modules/` unless it says otherwise.

## The five most likely next stops of the retail boot

Ordered by where they would fall after stop 13 of [retail_boot_chain.md](retail_boot_chain.md): by then the title
has created its device, queues, command lists, one placed resource and its first descriptor heap. The order is a
hypothesis.

| # | Area | What VIctory records | This runtime |
|---|---|---|---|
| 1 | Texture layouts (`xg.dll`) | `XGSuggestSwizzleMode` and `XGCreateTextureComputer` describe the resource with a `D3D12_RESOURCE_DESC` whose layout field holds `0x100 \| mode`. The computer fills a 0x1b40-byte layout: 15 mips of 0x70 bytes, 4 planes; the title reads the mip offsets at 0x00, 0x08, 0x10 and 0x1c. Slot 6 returns a 64-bit element offset that the title reads texels through (`xg.rs`) | Both exports and every computer slot from 2 up return `E_NOTIMPL` and write nothing, so slot 6 hands back 0x80004001 where an offset is read (`runtime/shims/xg_xs.cpp`) |
| 2 | DirectStorage (`xcrdapi.dll`) | Factory slots 4 (OpenFile), 5 (CreateStatusArray), 8 (SetStagingBufferSize: the title asks for 32 MiB and stops if it fails) and 10 (CreateQueue). A request is 0x48 bytes. The title polls status entry 0 in a `Sleep(1)` loop, so a request that never completes is a hang, not a crash. It closes queues with Close, not Release (`dstorage.rs`) | No `xcrdapi.dll` shim; stop 5 of the boot chain was cleared by an open upstream pull request (#4348) |
| 3 | XPackage interface id | The title asks `QueryApiImpl` for XPackageImpl as IXPackageImpl4 (`xpackage.rs`). Its chunk manager calls chunk availability, install, uninstall and enumeration | **Id done in this fork:** IXPackageImpl4 is accepted, with its one extra slot (41, `XPackageGetPackageKind`) answering `E_NOTIMPL` as the layout in `tools/gdk_runtime_classes.json` gives it (`runtime/shims/xgameruntime.cpp`). Still open: the chunk-manager slots answer `E_NOTIMPL` |
| 4 | Audio coprocessor | `AcpHal.dll` answers a command that carries an id with `COMMAND_COMPLETED` and sets the notification word to 1. The SHAPE context arrays come from the APU heap so their device addresses map back to them; the title uses only XMA contexts, and an XMA context is 16 words (`audio.rs`). `xapu.dll` and `chad.dll` are implemented (`apu.rs`, `dsp.rs`) | `runtime/shims/acphal.cpp` accepts commands and drops them, writes no notification word, and gives the context arrays synthetic APU addresses in the range its first `ApuAlloc` blocks also use. No `xapu.dll` or `chad.dll` shim; [audio_hal_exe_calls.md](audio_hal_exe_calls.md) records that the title reads 0 from `XDspConnect` as success |
| 5 | Title memory placement (`xmem.dll`) | The attribute word picks the address range: one flag bit places memory below 4 GiB, otherwise it lands between 4 GiB and 2^40, and the title's BVH builder refuses addresses above that. `XMemVirtualQuery` reports committed pages as graphics memory, which the BVH builder requires. `XMemAlloc` and `XMemFree` go through the title's exported `__XMemAllocationHooks__`, and the attribute's bits 24-28 give the log2 alignment (`xmem.rs`) | Page modes and placeholders are handled, but no address range is requested, the query leaves the extended fields zero, and `XMemAlloc` uses a fixed 64-byte alignment and ignores the hooks (`runtime/shims/xmem.cpp`) |

## Other differences

| Area | What VIctory records | This runtime |
|---|---|---|
| Console or PC | The title does not ask the runtime what device it is on: code linked into it reads `HKLM\Software\Microsoft\Windows NT\CurrentVersion\OEM`, value `ConsoleMode` (`RegOpenKeyW` or `RegOpenKeyExW`, then `RegQueryValueExW`), and takes a missing value for a PC. VIctory answers 0x64 for Series X and 0x60 for Series S (`xsystem.rs`); xcl records the same read in the thunk of `XCurl.dll`, and 0x68 for a Series devkit and 0x40, 0x50, 0x58 for Xbox One S, X and devkit | **Done in this fork:** the four registry functions are served under `advapi32.dll`, `kernel32.dll`, `kernelbase.dll` and the registry api sets, answer that one key from `XSystemGetDeviceType` (so `LEONIDA_DEVICE_TYPE` moves it; Pc, Unknown and the original Xbox One find no key) and pass every other key to the host (`runtime/shims/xgameruntime.cpp`, `xgameruntime_test`). Before, the host answered and the title saw a PC |
| GameInput by ordinal | The title imports `GameInputCreate` by ordinal 1 only (`gameinput.rs`) | **Done in this fork:** `gameinput.dll!#1` is registered too (`runtime/shims/gameinput.cpp`); before, an ordinal import fell back to the host's DLL or an unimplemented thunk (`runtime/src/pe_loader.cpp`). Still open: the keyboard as a device of its own ([gameinput.md](gameinput.md), VERIFY) |
| Relaunch | `XLaunchNewGame` does not return; the title relaunches itself with its path from `GetModuleFileNameA` (`xgame.rs`) | `XLaunchNewGame` logs and returns (`runtime/shims/xgameruntime.cpp`) |
| Main module identity | `GetModuleHandle(NULL)` and `GetModuleFileName*` answer with the title's image and path (`kernel.rs`) | They answer with `gta6rt.exe` ([xcl_compare.md](xcl_compare.md) lists the same difference) |
| Virtual memory range | `D3D12ConfigureVirtualMemoryX` writes the user-space range to its two outputs (`crates/victory-gpu/src/device.rs`) | It returns `S_OK` and writes nothing (`runtime/shims/d3d12_xs.cpp`) |
| Text entry | The title takes `E_ABORT` for "cancelled" and carries on; any other failure is an error (`xgameui.rs`) | **Done in this fork:** slots 17-19 start the async and complete it with `E_ABORT` and no text, and the size and result slots answer `E_ABORT` (`runtime/shims/xgameruntime_offline.cpp`); before, the call failed with `E_FAIL` before starting |
| CRT file opens | `fopen`, `_wfopen`, `_open`, `_wstat64`, `std::_Fiopen` and the others take virtual-drive paths too, as do `GetDiskFreeSpace(Ex)W` and `SetCurrentDirectoryA` (`files.rs`) | Only the kernel32 family maps `G:\` and `T:\` (`runtime/shims/file_system.cpp`) |

## Past boot stop 13: what TuxBox, OpenScarlett and G6Recomp record

Read at TuxBox `0b80c58` (Apache-2.0), OpenScarlett `87cdba6` (MIT) and G6Recomp `0b9e3c5` (GPL-3.0); see
[related_projects.md](related_projects.md). Paths are in each project's tree. TuxBox's run records are the only ones
of the three that reach past this repository's stops: its first run stopped on row 4, a later one reached the
player-selection prompt. A fact G6Recomp marks as reported from xcl is marked *(xcl)*. Nothing here repeats a title
address or interface id.

| # | Area | What they record | This runtime |
|---|---|---|---|
| 1 | Queue layout | Two console layouts. The newer: 16 `Signal`, 17 `Wait`, 18 timestamp frequency, 19 clock calibration, 20 `GetDesc`, 23 and 24 suspend and resume, 25 `SignalX(fence, value, flush flag 0 or 0x08000000)`, 31 a page-mapping update, 32 `PresentX`, 35 `ExecuteCommandListsX(count, lists, 64-bit frame token, flags)`. The older: 14 and 15 as on the PC, 23 `SignalX`, 30 `PresentX`. The title uses the newer one *(xcl)*, which fits this repository's own Intel-host run routing queue slot 35 ([retail_boot_intel_host.md](retail_boot_intel_host.md)). TuxBox picks the layout by the device interface the title asked for (`commands.rs`, `device.rs`); OpenScarlett and G6Recomp's notes describe the slots (`d3d12_xs_shim.cpp`, `d3d12x.md`) | **Done in this fork for the newer layout:** the device `D3D12XboxCreateDevice` returns gives its queues the console map (16-20 as the PC's 14-18, `GetDesc` in either argument order, 23/24, 25 with its flush word, 35 onto `ExecuteCommandLists`), 31 and 32 are logged and refused, and `LEONIDA_QUEUE_LAYOUT=pc` restores the PC map ([d3d12_command_objects.md](d3d12_command_objects.md), `xs_proxy_mock_test`). Before, PC order and every slot past 19 refused, so the title's `Signal` at 16 reached the PC's `GetTimestampFrequency`. The older layout is not served |
| 2 | Fence slot 12 | Past `ID3D12Fence1`'s public slots, slot 12 returns a stable CPU address of the fence's completed value, which the runtime keeps current and the title waits on (TuxBox `fence.rs`; G6Recomp `related-work.md`, *(xcl)*) | **Done in this fork:** served on every fence proxy, kept current by one watcher thread and by the proxy's own `Signal` and `GetCompletedValue` ([d3d12_command_objects.md](d3d12_command_objects.md), `xs_proxy_mock_test`, `queue_proxy_test`). Before, refused, which [retail_boot_intel_host.md](retail_boot_intel_host.md) records as stop 27 of that stack |
| 3 | Frame pacing | Device slots 78-81 are the frame interval, scheduling a frame event, waiting on one and the frame statistics. TuxBox records the title clearing its wait token before each polling wait (flags 2) and treating a failure as fatal, a flip superseding earlier origins, and a failed present still advancing the pacing (`frame_events.rs`). The interval call accepts only the console's refresh periods; the statistics records are 0x38 bytes (TuxBox; OpenScarlett places the times 8 bytes later, without a source) | 78-80 answer from a stub that writes a fresh token for every kind; 81 is refused. `runtime/src/frame_pacer.h` is not connected to the device proxy |
| 4 | Console depth format | TuxBox's first run stopped on device slot 25 for a 2560x1440 descriptor of console format 118 with flags 0x80300006 (depth, UAV and console bits), answered `UINT64_MAX`. It backs formats 118-120 with the D24S8 family, drops UAV on depth, drops the console flag bits above the PC's (keeping DCC's), and sizes console layouts 0x100-0x109 from the console layout (`format.rs`, `allocation.rs`) | No format 118, and resource flags past the PC set are refused (`runtime/shims/d3d12_vulkan_device.cpp`) |
| 5 | Present | `PresentX` takes planes of 72 bytes (token, count, resources, source rectangles, destination, colour space) and 32 bytes of parameters. What TuxBox accepts implies one plane with one 3840x2160 resource from 2 display resources; the title draws into its own top-level window, which TuxBox reuses (`commands.rs`, `present.rs`, `window.rs`) | The present core exists (`runtime/shims/xbox_present.cpp`), with no queue route and no window adoption |
| 6 | Command-list slots | Console list slots 27 `ExecuteBundle`, 28-30 queries, 31 `SetPredication`, 32-55 the PC's 28-51, 56-58 markers and events, 61 `ExecuteIndirect`, 83 and 85 a 7-argument texture copy (the title's uploader uses 85), 139 a reset with a flags argument the title uses *(xcl)* (OpenScarlett `d3d12_xs_shim.cpp`, TuxBox `commands.rs`) | 27-30 dropped, 56-59 forwarded to PC slots that differ, 139 dropped ([d3d12_command_objects.md](d3d12_command_objects.md) has this repository's own partial table) |
| 7 | Device slots | Console 83-106 are the PC's 44-67, 108-112 the PC's 68-72, 115 deserializes a state object, 127 is a committed resource with a layout; 57 and 67 deserialize console pipelines, 60 is the graphics pipeline, 61 a sampler from 21 dwords, 69 a driver hint, 70 and 71 views without a resource, 74 and 75 register and unregister a page pool, 86 the pipeline-stream create (OpenScarlett, TuxBox `device.rs`) | Several of these reach PC methods of the same number: 57 `CreateLifetimeTracker` (refused thousands of times in the Intel-host run), 69 `CreateCommittedResource2`, 74 `ShaderCacheControl`, 75 is taken for `CreateCommandQueue1`; 80 and up refused |
| 8 | Pipelines | Rectangle lists (topology 0x11, topology type 0x13) for the title's full-screen passes *(xcl)*; console stream tags 23 and 24 for amplification and mesh, one below the PC's, and a 32-byte stencil record 26; after a failed pipeline the title later uses a freed object, so TuxBox returns pipelines that do nothing (`rectangle.rs`, `stream.rs`, `fallback.rs`) | Topology type 19 refused, PC stream tags, no fallback pipeline |
| 9 | Audio | The title connects `xapu.dll` (Opus) and `chad.dll` (convolution) at startup, and a failed `XDsp` connect ends at a title breakpoint (TuxBox evidence and `xapu`; G6Recomp *(xcl)*). `ApuAlloc`'s flag bit 0 means cached (OpenScarlett, citing the SDK header) | No `xapu.dll` or `chad.dll` shim; `acphal.cpp` treats flags 0 and 1 alike |
| 10 | Virtual memory | `D3D12ConfigureVirtualMemoryX` gets a block that is zero but for the word at +4, 4 (G6Recomp `boot.md`, measured on the title); TuxBox reads flags at +0, the count at +4 and a preserve size at +8, and writes the start at +16 and the limit at +24 (`exports.rs`) | Returns `S_OK` and writes nothing (`runtime/shims/d3d12_xs.cpp`) |
| 11 | DirectStorage | The queue description is 0x18 bytes, 0x20 at factory slot 10, whose extra word the title sets to 1; requests are 0x48 bytes; status entries start as `E_PENDING`; factory slot 8 asks for 32 MiB and a failure of slot 8 or 4 ends at an assert (G6Recomp `direct_storage.h`, `io.md`, `boot.md`) | No `xcrdapi.dll` shim (row 2 above) |
| 12 | Queue creation | Slot 48's description is type, options, a queue index up to 3 and an engine index; the title's compute queues carry 2 and 3 in the third word (TuxBox `device.rs`) | Read as the PC description with its flags masked, so a 3 there reads as `DISABLE_GPU_TIMEOUT` (low risk) |
